# UI framework decision: egui prototype results

Date: 2026-11-05. Scope: spec §9 item 4 — validate that an immediate-mode egui shell can
drive a dual-pane text view over ≥100 MB inputs before committing the GUI layer.

## Verdict

**egui/eframe is viable for the text view; adopt it for M1 and keep the engine crates
framework-agnostic so the decision stays reversible.** The prototype scrolls two 110 MB
files at the display refresh rate with ~1 ms of CPU per frame and opens each file in
under 100 ms. The remaining risks (custom text editing, IME, printing) are not about
performance and are listed below with mitigations.

## Setup

| item | value |
|---|---|
| machine | Windows 11 Pro 10.0.26100, x86_64 |
| toolchain | rustc 1.99.1, eframe 0.37 (glow backend), memmap2 0.9 |
| build | `cargo build --release -p bcompare` (opt-level 3, debug=1) |
| inputs | `tmp/left.txt`, `tmp/right.txt`: 110 000 043 bytes each, 2 119 483 lines each, synthetic word soup (generated by a one-off Python snippet, not checked in) |
| command | `target\release\matcha.exe tmp\left.txt tmp\right.txt --bench=600` |
| pattern | per frame: 3 frames of smooth scrolling (+3 rows) then one random jump anywhere in the file; 30 warm-up frames discarded |
| rendering | both panes drawn every frame via `ScrollArea::show_rows` (only visible rows materialised), monospace 13 px, line-number gutter, lines truncated at 2048 bytes, scroll offsets locked between panes |

## Measurements

Open + index (mmap the file, scan for `\n`, store `u32` line starts):

| metric | left | right |
|---|---|---|
| load + index time | 77 ms | 77 ms |
| line index size | 8.5 MB | 8.5 MB |

Frame cost over 600 measured frames (two panes, 85 rows drawn per frame in total):

| metric | mean | p50 | p95 | p99 | max |
|---|---|---|---|---|---|
| `App::ui` wall time (ms) | 0.71 | 0.71 | 0.93 | 1.07 | 1.30 |
| eframe `cpu_usage` per frame (ms) | 1.07 | 1.06 | 1.39 | 1.64 | 1.86 |

Throughput: 59.9 fps overall, i.e. capped by vsync, not by the UI. The window stayed
responsive during the run (hover/drag on either scrollbar re-syncs the other pane).

Memory (sampled with `Get-Process` 5 s into a second run):

| metric | value |
|---|---|
| private bytes | 137 MB |
| working set | 320 MB |

The working set includes the file-backed mmap pages that the indexer touched (220 MB);
they are clean pages the OS can drop at any time. Private memory is dominated by the GPU
context plus the 17 MB of line indexes — no copy of the file content is ever made, which
satisfies spec §7 ("禁止整文件多次复制").

A second run (`--bench=400`) reproduced the numbers within noise (update mean 0.75 ms,
frame CPU mean 1.20 ms, p99 1.91 ms).

## What the prototype does *not* show yet

- **Alignment gaps and difference colouring.** Rows were positional (line n ↔ line n).
  Rendering from an `AlignMap` adds one indirection per row and a background rect per
  row; both are O(visible rows) and will not change the picture.
- **Syntax highlighting.** Per-row tokenisation of 85 lines/frame is cheap; the risk is
  pathological lines (minified JS). Mitigation already in place: render cap per line and
  tokenise lazily per visible row with a small LRU.
- **Editing.** egui's `TextEdit` is not suitable for a multi-megabyte editor; the plan is
  a custom widget (the equivalent of `TUiTextEditor`) painting glyph runs from the
  `LineList` and handling the caret itself. This is work, but it is the same work BC did
  on VCL, and immediate mode makes a virtualised editor simpler, not harder.
- **IME / accessibility.** egui has basic IME support on Windows (winit); CJK composition
  in a custom editor needs verification. AccessKit integration exists in eframe.
- **Printing / HTML report preview.** Not an egui strength; reports are generated as
  files and opened externally (BC also shells out to a browser for HTML reports).

## Alternatives considered

| framework | pros | cons | decision |
|---|---|---|---|
| **egui / eframe** (tested) | pure Rust, single binary, trivial virtualisation, fast iteration, custom painting is natural | no native look, custom text editor required, weaker IME/a11y story | **adopt for M1** |
| iced | retained Elm architecture, good widgets, pure Rust | large text views need a custom widget just the same; slower iteration; less mature custom painting APIs | fallback if egui's editor path fails |
| Tauri + web view | best text rendering/IME for free (Monaco-style editors exist), HTML reports natively | 100 MB virtualisation must be rebuilt in JS; IPC boundary between Rust engines and DOM; two toolchains; WebView2 dependency | rejected for the core views; still an option for report preview |
| slint | declarative, good native feel | commercial licence considerations for some uses; custom large-text widget required | not pursued |
| native Win32/Direct2D | maximal control and fidelity to BC | Windows-only, large effort, contradicts the macOS/Linux outlook in spec §7 | rejected |

## Consequences for the architecture

1. `bc-gui` stays the only crate that depends on eframe; engines expose row/token
   iterators, never widgets.
2. The next GUI task is the custom text widget over `bc_engine_text::TextMap`
   (gutter, aligned gaps, difference colours, selection, caret), followed by the folder
   tree (`DirTreeView`) which has the same virtual-row structure.
3. Re-run `matcha --bench` after each major rendering change; keep update p99 under 4 ms
   and frame CPU p99 under 8 ms to preserve the 16 ms budget with headroom for the engine.

## How to reproduce

```powershell
# generate inputs (any two large text files work; ~110 MB each were used here)
cargo build --release -p bcompare
.\target\release\matcha.exe <left> <right> --bench=600
```

The benchmark prints `bench.*` key/value lines to stdout and closes the window.

### 复测环境与方法

- 同机 Windows 11 / Rust 1.99.1 / egui、eframe 0.37 / glow / release。
- `tmp/left.txt`、`tmp/right.txt` 各 110,000,043 B、2,119,483 来源行，输入未改写。
- `cargo build --release -p bcompare` 后运行
  `target/release/matcha.exe tmp/left.txt tmp/right.txt --bench=600`。
- 等待真实 Align2Job 完成后才进入 30 帧预热和 600 帧计量；仍是三次 +3 行滚动、
  一次随机跳转的固定模式。表中不是无对齐或简化渲染基准。
- 只为可见行排版；长行每次最多 4096 字节的水平窗口；过滤索引按区段、缩略图
  按 512 桶缓存，统计不在每帧重算。

| 600 帧轮次 | update mean / p99 ms | frame CPU mean / p99 ms | 单侧加载 ms |
|---|---:|---:|---:|
| 复测 1 | 0.618 / 1.104 | 1.053 / 1.762 | 132 / 130 |
| 复测 2 | 0.626 / 1.174 | 1.074 / 1.810 | 132 / 129 |
| Tab 修正后 | 0.614 / 1.163 | 1.068 / 1.646 | 135 / 137 |
| 最终（光标边界修正后） | **0.613 / 1.129** | **1.072 / 1.688** | **134 / 133** |

最终 update p50/p95/max = 0.524/0.973/1.354 ms；frame CPU p50/p95/max =
1.035/1.538/2.009 ms。每帧两侧合计约 78 行，比原型少是因为新增命令/双侧状态区
占用了部分高度。全部轮次满足 **update p99 <4 ms / CPU p99 <8 ms**；相较原型
尾部耗时有小幅波动，未声称每一个百分位都严格优于原型。

保留全部原 `bench.*` 键与格式。`bench.wall_seconds=11.61` /
`bench.fps_overall=54.3` 包括前置比较等待时间，而统计样本仅计算等待后的帧，
因此不能把该 overall fps 解释成稳态刷新率。`bench.index_mb=101.7` 现在表示
两侧引擎 Line 元数据的估计大小（行范围+逐行行尾），不再是原型的 u32 起点表。
这里没有重新测量 GUI 峰值私有内存，也不把基准日志当作峰值内存证明。

### egui 0.37 接线注意

- eframe 使用 `App::ui(&mut self, ui, frame)`，不是旧版 update(Context, ...)。
- `egui::Panel::top/bottom(...).show(ui, ...)` 以根 Ui 为入口；
  `ScrollArea::show_rows` 的行高加间距必须一致，正式文本行间距设为 0。
- 从 `output.state.clamped_offset()` 取得偏移，不依赖旧 state.offset 字段；
  顶层全局样式使用 `ctx.all_styles_mut`。
- 子 Ui 默认继承布局，Over-Under 的父容器必须显式 top_down，不能在横向容器中
  连续 allocate_ui 后假定它们会纵向排列。
- `Id::unique`、`DroppedFile::path()`、typed CharIndex/ByteIndex 及
  `ctx.request_screenshot(callback)` 均采用 0.37 API。
- 无 GPU 的测试必须显式 clear 未上传的 textures_delta；测试仍执行真实 tessellate，
  原生程序则正常由 backend 应用纹理。
- 文件夹线合并只需扩展 app 的 View/action 分支与 Home 入口，勿重新引入原型
  LoadedText 或第二份全量文本缓冲。
